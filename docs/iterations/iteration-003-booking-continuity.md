# 迭代 003：让一次选择被看见、被保留

日期：2026-08-22

## 受众与核心记忆点

- 主要受众：28–45 岁、在意建筑、自然环境与安静节奏，正在比较精品度假酒店的情侣、独行或小家庭旅行者。
- 他们当前的任务：先判断品牌是否符合自己的旅行方式，再快速确认目的地、日期和住客人数能否进入一个可信的规划流程。
- 最希望留下的记忆：**酒店退后，让地方成为主角。** Lumen House 不是用同一种豪华复制每个目的地，而是让每次停留保留当地本来的尺度和时间。

## 本轮只解决的一个问题

首页搜索与预订页之间缺少交互连续性。用户填写日期和人数后，点击“查询可订房”会立刻跳页，页面没有说明是否接收了操作；跳转时只传递目的地，预订页又显示固定日期、固定住客和固定总价。用户容易认为刚才的选择没有生效。

本轮不重写品牌文案、不增加新页面，也不改变既有视觉方向，只修复“选择没有被确认和保留”这一条反馈断层。

## 修改前现状

| 环节 | 修改前 |
| --- | --- |
| 首页预订栏 | 日期和住客为非受控字段，提交只传目的地 |
| 顶部预订抽屉 | 只保留目的地，日期与住客在跳转时丢失 |
| 提交反馈 | 点击后立即跳页，无进行中、错误或确认状态 |
| 预订页第一步 | 始终显示固定的默认值 |
| 确认页 | 日期、住客和总价均为硬编码 |

## 依据与证据等级

- A：用户要求先明确“给谁看、最想让对方记住什么”，并针对一个具体问题完成调整。
- B：代码检查确认两个首页入口都没有保留完整搜索条件，预订页也没有读取地址参数。
- C：酒店规划属于连续任务；输入被确认并在下一页保持，是建立可信感的基础反馈。

## 迭代理念

高级感不只来自图片和留白，也来自系统对用户意图的安静回应。反馈不使用夸张弹窗，而用三段连续信号完成：

1. 点击后按钮进入“正在准备”状态；
2. 输入有误时在原位置说明原因；
3. 下一页明确提示“已带入”，并继续使用同一组条件。

## 设计与实现方法

- 将目的地集中为一份共享数据，首页预订栏、侧边预订抽屉和预订页使用相同的值与名称。
- 将目的地、入住、离店和住客改为受控字段；离店日期不能早于或等于入住日期。
- 提交后保留 420ms 的轻量状态反馈，再把目的地、日期、成人和儿童人数作为地址参数带入预订页。
- 预订页在首帧后读取参数并回填，避免服务器与浏览器首屏内容不一致。
- 房型步骤增加“已保留”摘要；确认页与完成页继续显示同一组日期和住客。
- 根据入住与离店日期计算晚数和预计总价，替换固定三晚价格。
- 反馈使用小圆点、文字和按钮状态，不增加弹窗；错误、进行中与普通提示拥有不同但克制的颜色。
- 移动端沿用原有隐藏日期栏的布局，默认日期仍会被带入；抽屉中可完整修改所有条件。

## 验证结果

- `npm run lint`：通过。
- `npm run build:pages`：通过，首页、酒店名录、详情和预订页均成功静态生成。
- TypeScript 校验：通过。
- 日期范围、共享目的地数据、参数生成、参数回填和动态价格均进入编译路径。
- 本轮未进行浏览器视觉检查；没有把未执行的视觉检查写成已验证结果。

## 遗留项与下一步

- 当前仍是课程用前端演示，不接真实库存、支付或个人资料后台。
- 不同目的地仍共用两种演示房型；如果下一轮继续完善可信度，应让各目的地拥有独立房型数据，但不要和本轮反馈调整混在一起。
- 品牌主张已经明确，但本轮没有改写首屏文案；后续只有在用户测试证明英文主标题无法传达“地方优先”时，再单独做内容表达迭代。
